## 五、主要问题及影响分析

1. **BUG_LOGIN_001（登录无防暴力破解）**：账号可被无限次尝试密码，存在被爆破的安全隐患。非阻断性问题，但建议增加连续失败锁定/验证码加强机制，优先级中。

2. **BUG_LOGIN_002（缺 code 字段空指针）**：登录接口请求体缺少 `code` 字段时，`SysLoginService.validateCaptcha` 里 `code.equalsIgnoreCase(captcha)` 对 null 直接空指针，接口返回 `{"code":500,"msg":null}`。属接口健壮性缺陷，应补空值判断并返回友好提示（如"验证码不能为空"）。复现：`POST /login` 只传 username/password/uuid、不传 code 字段即可必现。

3. **BUG_USER_001（手机号无格式校验）**：`SysUser` 实体对 `phonenumber` 字段只加了 `@Size(max=11)` 长度校验，没有 `@Pattern` 正则，导致字母也能保存。影响数据质量，建议补充 11 位数字正则。

4. **BUG_USER_002（昵称空值 500 + 信息泄露）**：`SysUser` 实体对 `nickName` 字段只加了 `@Xss`/`@Size`，没有 `@NotBlank`，且 `insertUser` 对昵称做了空值过滤，导致昵称为空时 SQL 不含 `nick_name` 列、数据库 NOT NULL 约束报错，接口返回 `{"code":500}`，msg 直接把完整 SQL 语句和表结构返回给前端，属校验缺失 + 异常信息泄露。建议补 `@NotBlank` 并统一异常返回。

5. **BUG_ROLE_001（数据权限刷新）**：源码 `edit` 方法仅调用了 `refreshPermissionByRoleId`，数据权限范围变更后在线用户是否需要重新登录待验证。

## 八、经验总结

1. **读源码设计用例，比拍脑袋猜高效得多**：从 `SysUser.java` 的校验注解里，直接挖出"手机号无正则"这个 Bug，说明白盒思维对黑盒测试有巨大帮助。

2. **边界值用例发现 Bug 最多**：密码 4/5/20/21、手机号 10/11/12 这些边界，是这次测试里出问题最多的地方，后续用例设计继续加强边界覆盖。

3. **数据权限是后台测试的精华**：5 种数据范围 + 越权测试，覆盖了普通功能测试覆盖不到的安全维度，是这次测试最有价值的产出。

4. **SQL 验证是测试的基本功**：逻辑删除、关联表清理、密码密文这些点，都必须靠 SQL 才能验证，前端"看起来对了"不等于"数据真的对了"。
