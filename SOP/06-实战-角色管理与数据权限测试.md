# 06 — 实战：角色管理与数据权限测试（深入版）

> 基于 RuoYi 真实源码设计的深入用例。**这是整个项目里最能拉开差距的模块**——因为它练的是后台系统最核心、也最容易被初级测试忽略的「权限模型 + 数据权限（越权测试）」。

---

## 零、真实逻辑（先搞懂 RBAC 和数据权限）

### 0.1 角色表 sys_role 结构

| 字段 | 类型 | 说明 | 校验 |
|------|------|------|------|
| role_id | bigint | 角色ID | 主键自增 |
| role_name | varchar(30) NOT NULL | 角色名称 | `@NotBlank` + `@Size(max=30)` |
| role_key | varchar(100) NOT NULL | 权限字符（如 admin/common） | `@NotBlank` + `@Size(max=100)` |
| role_sort | int(4) NOT NULL | 显示顺序 | `@NotNull` |
| data_scope | char(1) default '1' | 数据范围 | 无校验 |
| menu_check_strictly | tinyint(1) default 1 | 菜单树父子是否关联 | - |
| dept_check_strictly | tinyint(1) default 1 | 部门树父子是否关联 | - |
| status | char(1) | 状态（0正常 1停用） | - |
| del_flag | char(1) default '0' | 删除标志（逻辑删除） | - |

### 0.2 数据权限 data_scope 的 5 种取值（核心中的核心）

| 值 | 含义 | 数据过滤效果 |
|----|------|-------------|
| 1 | 所有数据权限 | 能看到全部数据 |
| 2 | 自定义数据权限 | 只能看到部门树里勾选的部门数据 |
| 3 | 本部门数据权限 | 只能看到自己所在部门的数据 |
| 4 | 本部门及以下 | 自己部门 + 所有下级部门数据 |
| 5 | 仅本人数据权限 | 只能看到自己创建的数据 |

> 数据权限靠 `@DataScope` 注解 + AOP 实现：在 Mapper 查询时自动给 SQL 拼 `WHERE` 条件。**这是越权测试的核心对象**——同一张表，不同角色查出来的行数不一样。

### 0.3 RBAC 权限模型（RuoYi 是标准 RBAC）

```
用户 sys_user ──多对多── 角色 sys_role ──多对多── 菜单 sys_menu
                    │
                    └──多对多── 部门 sys_dept（数据权限）
```

中间表：`sys_user_role`（用户-角色）、`sys_role_menu`（角色-菜单）、`sys_role_dept`（角色-部门）。

### 0.4 关键业务规则（源码确认）

| 规则 | 源码事实 | 测试意义 |
|------|----------|----------|
| 超级管理员角色保护 | `checkRoleAllowed`：roleId=1 抛"不允许操作超级管理员角色" | admin 角色不能改/删/停用/改数据权限 |
| 角色名唯一 | `checkRoleNameUnique` | 同名必拦 |
| 权限字符唯一 | `checkRoleKeyUnique` | 同 roleKey 必拦 |
| 已分配不能删除 | 删除前 `countUserRoleByRoleId>0` → "xxx已分配,不能删除" | 有用户的角色删不掉 |
| 删除级联清理 | 删除时同步删 `sys_role_menu`、`sys_role_dept` | 关联表不留脏数据 |
| 修改角色刷新在线权限 | 改角色后 `refreshPermissionByRoleId` | 在线用户权限即时生效 |
| 逻辑删除 | del_flag='2' | 同用户管理 |

### 0.5 16 个接口一览

```
GET    /system/role/list                   角色列表
POST   /system/role/export                 导出
GET    /system/role/{roleId}               角色详情
POST   /system/role                        新增角色
PUT    /system/role                        修改角色
PUT    /system/role/dataScope              修改数据权限
PUT    /system/role/changeStatus           状态修改
DELETE /system/role/{roleIds}              删除角色
GET    /system/role/optionselect           角色下拉列表
GET    /system/role/authUser/allocatedList     已分配用户列表
GET    /system/role/authUser/unallocatedList   未分配用户列表
PUT    /system/role/authUser/cancel            取消授权单个用户
PUT    /system/role/authUser/cancelAll         批量取消授权
PUT    /system/role/authUser/selectAll         批量授权用户
GET    /system/role/deptTree/{roleId}          角色部门树
```

## 二、数据权限测试（核心，14 条）

> 这是本模块最有价值的部分。数据权限 = **同一个查询接口，不同角色返回不同行数**。测试思路：造一个跨部门的多用户场景，然后分别用不同 data_scope 的角色登录，对比能看到的数据范围。

### 2.1 测试数据准备

先用 admin 造数据（面试时可以讲"我构造了测试场景数据"）：

```
部门结构：
  总公司(100)
    ├── 研发部(103)
    │     └── 测试组(106)
    └── 市场部(105)

用户：
  u_all    → 属于研发部，数据权限=1（所有）
  u_custom → 属于研发部，数据权限=2（自定义：只勾测试组）
  u_self   → 属于研发部，数据权限=3（本部门）
  u_below  → 属于研发部，数据权限=4（本部门及以下）
  u_mine   → 属于研发部，数据权限=5（仅本人）
```

### 2.2 数据权限用例

| 编号 | 用例标题 | 优先级 | 步骤 | 预期结果 |
|------|----------|--------|------|----------|
| ROLE_015 | 数据权限=1（所有） | 高 | 用 u_all 登录查用户列表 | 能看到全部部门的用户 |
| ROLE_016 | 数据权限=2（自定义-勾选部门） | 高 | 用 u_custom 登录查用户列表 | 只能看到勾选的"测试组"部门用户 |
| ROLE_017 | 数据权限=3（本部门） | 高 | 用 u_self 登录查用户列表 | 只能看到"研发部"本部门用户 |
| ROLE_018 | 数据权限=4（本部门及以下） | 高 | 用 u_below 登录查用户列表 | 能看到研发部 + 测试组用户，看不到市场部 |
| ROLE_019 | 数据权限=5（仅本人） | 高 | 用 u_mine 登录查用户列表 | 只能看到自己 |
| ROLE_020 | 数据权限=2 不勾任何部门 | 中 | 自定义但部门树不勾选 | 按实际：查不到数据或全查（如实记录，可能是 Bug） |
| ROLE_021 | 修改数据权限为"本部门" | 高 | 把某角色 data_scope 从 1 改成 3 | 该角色用户登录后数据范围立即收窄 |
| ROLE_022 | 数据权限修改后在线用户生效 | 中 | 改 data_scope 时用户已在线 | 按实际：是否需重新登录（源码 refreshPermission 只刷角色权限，数据权限可能需重登） |
| ROLE_023 | 普通角色操作数据权限 | 中 | 用非 admin 角色改 data_scope | 返回"没有权限访问角色数据"（数据权限拦截） |
| ROLE_024 | 改 admin 角色的数据权限 | 高 | 尝试改超级管理员 data_scope | **返回"不允许操作超级管理员角色"** |
| ROLE_025 | 部门树勾选父子关联 | 中 | 勾选"研发部"观察"测试组" | 勾父自动勾子（menu/dept_check_strictly=1 时） |
| ROLE_026 | 部门树取消父子关联 | 低 | 关闭"父子关联"再勾选 | 勾父不勾子，可单独勾选 |
| ROLE_027 | 数据权限=4 下查子部门 | 中 | u_below 查测试组数据 | 能看到（含下级） |
| ROLE_028 | 数据权限=3 下查子部门 | 中 | u_self 查测试组数据 | 看不到（本部门不含下级） |

**数据权限的面试讲法**：

> "我重点测了 RuoYi 的数据权限。RuoYi 有 5 种数据范围——全部/自定义/本部门/本部门及以下/仅本人。我构造了一个跨部门的测试场景，用 5 个不同 data_scope 的角色分别登录查用户列表，对比返回的行数，验证每个范围的数据过滤是否正确。这其实是越权测试的一种——保证低权限用户看不到不该看的数据。"

## 六、数据库验证 SQL

```sql
-- 1. 角色基础数据
SELECT role_id, role_name, role_key, role_sort, data_scope, status, del_flag
FROM sys_role;

-- 2. 角色-菜单关联（分配菜单后验证）
SELECT r.role_name, m.menu_name, m.perms
FROM sys_role r
JOIN sys_role_menu rm ON r.role_id = rm.role_id
JOIN sys_menu m ON rm.menu_id = m.menu_id
WHERE r.role_name = '测试角色';

-- 3. 角色-部门关联（数据权限=2 自定义时）
SELECT r.role_name, d.dept_name
FROM sys_role r
JOIN sys_role_dept rd ON r.role_id = rd.role_id
JOIN sys_dept d ON rd.dept_id = d.dept_id
WHERE r.role_name = '测试角色';

-- 4. 角色-用户关联（分配用户后验证）
SELECT r.role_name, u.user_name
FROM sys_role r
JOIN sys_user_role ur ON r.role_id = ur.role_id
JOIN sys_user u ON ur.user_id = u.user_id
WHERE r.role_name = '测试角色';

-- 5. 删除角色后，验证关联表无残留【关键】
SELECT * FROM sys_role_menu WHERE role_id = (SELECT role_id FROM sys_role WHERE role_name='测试角色' AND del_flag='2');
-- 预期：0 行（删除时级联清理了）

-- 6. 验证数据权限实际过滤效果：对比两个角色查用户列表
-- 用 u_self（本部门）登录后，等价 SQL：
SELECT * FROM sys_user u
WHERE u.dept_id = (SELECT dept_id FROM sys_user WHERE user_name='u_self');
-- 预期：只返回本部门用户
```

## 七、Bug 报告示例

### Bug：数据权限修改后，在线用户数据范围未即时生效

```markdown
【Bug 编号】BUG_ROLE_001
【模块】角色管理-数据权限
【标题】[数据权限] 修改角色数据范围后，已在线用户的数据权限未即时刷新

【严重程度】一般
【优先级】中

【环境】Chrome 120 / Spring Boot 2.5.15 / MySQL 8.0 / Redis

【前置条件】
1. 角色"测试角色" data_scope=1（所有数据权限）
2. 用户 u_test 持有该角色，且已登录

【复现步骤】
1. admin 把"测试角色"的 data_scope 从 1 改成 3（本部门）
2. u_test 不重新登录，直接刷新用户列表

【实际结果】
u_test 仍能看到全部部门的用户（数据范围未收窄）
（源码仅调用了 refreshPermissionByRoleId 刷新角色权限，未刷新数据权限缓存）

【预期结果】
数据权限修改后，该角色所有在线用户应立即按新范围过滤数据

【复现频率】必现

【附件】修改前后两次列表查询结果对比截图
```

> 注：这个 Bug 是否真的存在，以你实际跑出来的结果为准。源码里 `edit` 方法确实只调了 `refreshPermissionByRoleId`，数据权限的 SQL 过滤是在查询时实时拼的，所以可能**实际是即时生效的**。测的时候如实记录，发现差异就提 Bug，没差异就说明你验证过"修改即时生效"这条正向用例。

## 八、角色管理模块测试总结

| 维度 | 覆盖情况 |
|------|----------|
| 角色 CRUD | 14 条：空值、唯一性、长度、admin 保护、已分配保护 |
| 数据权限 | 14 条：5 种数据范围、自定义部门、父子联动、越权 |
| 菜单授权 | 8 条：父子联动、孤立按钮、删除级联清理 |
| 用户授权 | 8 条：批量授权/取消、停用角色影响 |
| 权限越权 | 6 条：按钮权限、数据权限、未登录 |
| 数据库验证 | 6 组 SQL：三张关联表 + 级联清理 + 数据范围对比 |

**你在这个模块练到的核心能力**：

1. **RBAC 权限模型理解** —— 用户-角色-菜单 三张表的多对多关系
2. **数据权限（越权测试）** —— 5 种数据范围，同一接口不同角色返回不同数据
3. **级联删除验证** —— 删除角色后关联表是否清理
4. **保护规则测试** —— admin 角色保护、已分配角色保护
5. **关联表 SQL** —— 三表 JOIN、脏数据检查

面试可以这样讲：

> "角色管理是我测得最深的模块。我搞懂了 RuoYi 的 RBAC 模型——用户、角色、菜单三张表多对多关联，还重点测了数据权限。RuoYi 有 5 种数据范围，我构造了跨部门场景，用 5 个不同 data_scope 的角色分别登录对比数据范围。这本质上是越权测试，验证低权限用户看不到越权数据。我还测了 admin 角色保护和'已分配角色不能删除'这些边界，删角色时验证了关联表是否级联清理。"

## 附：和前面模块串成完整闭环

到这里，你已经覆盖了后台系统的完整权限链路：

```
登录模块（02）→ 用户管理（03）→ 角色管理+数据权限（06）
     │                │                    │
  入口认证         数据实体            权限分配+越权
```
