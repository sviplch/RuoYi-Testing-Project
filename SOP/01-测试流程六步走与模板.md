# 01 — 测试流程六步走与全套模板

---

## 一、测试完整流程（六步走）

```
第一步：需求分析 —— 搞懂功能是什么、用户是谁、边界在哪
    ↓
第二步：测试计划 —— 明确测什么、怎么测、测多久
    ↓
第三步：用例设计 —— 等价类+边界值+场景法，写测试用例
    ↓
第四步：用例评审 —— 自己检查一遍有没有漏
    ↓
第五步：测试执行 —— 搭环境、跑用例、提Bug、跟踪修复
    ↓
第六步：测试报告 —— 总结结果，给出质量结论
```

下面每一节给一个**可以直接填的模板**，填完就是你面试时的项目经历。

## 二、模板 1：测试计划

```markdown
# 测试计划

## 一、测试目标
本次测试对【XXX系统】【XXX模块】进行功能测试和接口测试，
验证其是否满足需求文档要求，发现潜在缺陷，评估质量水平。

## 二、测试范围
- 测试对象：【登录模块】【用户管理模块】
- 测试类型：功能测试、接口测试、异常测试
- 不测内容：性能压测（本次不做）

## 三、测试环境
- 操作系统：Windows 11
- 后端：Spring Boot 2.x（端口 8080）
- 前端：Vue + Element UI（端口 80）
- 数据库：MySQL 8.0
- 浏览器：Chrome、Edge

## 四、测试策略
- 功能测试：黑盒测试，等价类 + 边界值 + 场景法
- 接口测试：Postman，覆盖正常/异常参数
- 数据库验证：测试后用 SQL 核对数据落库情况

## 五、测试资源
- 测试人员：1 人（本人）
- 测试时间：X 天

## 六、风险
- 环境依赖 Redis，若未启动会导致后端异常
- 部分功能权限受限，需用 admin 账号
```

## 三、模板 2：测试用例

**用例字段说明**：

| 字段 | 说明 |
|------|------|
| **用例编号** | 唯一，如 LOGIN_001 |
| **模块** | 所属功能模块 |
| **用例标题** | 一句话说清测什么 |
| **优先级** | 高/中/低 |
| **前置条件** | 执行前需要满足的状态 |
| **测试步骤** | 编号，动宾结构，可操作 |
| **输入数据** | 具体填什么 |
| **预期结果** | 明确的、可验证的结果 |
| **实际结果** | 执行后填 |
| **是否通过** | 通过/失败 |

**用例表格模板（Excel/飞书表格都行）**：

```
用例编号 | 模块 | 用例标题 | 优先级 | 前置条件 | 测试步骤 | 输入数据 | 预期结果 | 实际结果 | 是否通过
---------|------|----------|--------|----------|----------|----------|----------|----------|----------
LOGIN_001| 登录 | 正确账号密码登录成功 | 高 | 系统已启动 | 1.打开登录页 2.输入账号密码 3.点击登录 | admin/admin123 | 登录成功，跳转首页，返回Token | | 
```

## 四、模板 3：Bug 报告

```markdown
# Bug 报告单

【Bug 编号】BUG_001
【所属模块】登录模块
【Bug 标题】[登录] 输入错误密码连续 5 次后未触发任何限制

【严重程度】严重 / 一般 / 轻微
（严重=核心功能不可用；一般=功能异常但有规避方法；轻微=不影响使用）

【优先级】高 / 中 / 低

【测试环境】
- 后端版本：Spring Boot 2.x
- 前端：Vue 2 + Element UI
- 浏览器：Chrome 120
- 数据库：MySQL 8.0
- 测试账号：admin

【前置条件】
系统已启动，打开登录页面

【复现步骤】
1. 打开登录页 http://localhost
2. 用户名输入 admin，密码输入错误值 123456
3. 点击登录按钮
4. 重复步骤 2-3 共 10 次

【实际结果】
第 10 次仍然只是提示"用户不存在/密码错误"，没有出现验证码、没有账号锁定

【预期结果】
连续输错 5 次后应出现验证码或锁定账号（安全要求）

【复现频率】必现（10/10 次）

【附件】
- 截图：第 10 次登录失败提示
- 抓包：登录接口返回的响应体
```

## 六、测试过程中每天做什么

| 时间 | 工作内容 |
|------|----------|
| **第1天** | 搭环境、熟悉系统、读需求、梳理测试点 |
| **第2天** | 写测试计划 + 登录模块测试用例 |
| **第3天** | 执行登录用例，用 Postman 测接口，发现 Bug 就记 |
| **第4天** | 写用户管理模块用例 + 执行，用 SQL 验证数据 |
| **第5天** | 回归测试（重跑之前失败的用例）、写测试报告 |

---

## 七、关键心法

1. **用例要能复现**：别人拿着你的用例，不看你人，也能测出一样的结果
2. **预期结果要具体**：不是"显示正确"，而是"返回 HTTP 200，响应体 code=200，页面提示登录成功"
3. **多查数据库**：前端显示成功 ≠ 数据真的写进去了，一定要 SQL 核对
4. **Bug 要留证据**：截图 + 接口返回 + 日志，一个都不能少
