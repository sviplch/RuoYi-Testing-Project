# 03 — 实战：用户管理模块测试（深入版）

> 基于 RuoYi 真实源码和 `sys_user` 表结构设计的深入用例。用户管理是后台系统最核心的 CRUD 模块，也是面试最能拉开差距的地方——**别人只会测"新增能成功"，你能测出"删了其实没删、手机号能输字母、空昵称居然报错"这些底层事实。**

---

## 零、用户管理真实逻辑（先搞懂再测）

从源码 `SysUserController.java`、`SysUserServiceImpl.java`、`SysUser.java` 和建表脚本确认的事实：

### 0.1 字段校验规则（来自实体类注解，最权威）

| 字段 | 数据库类型 | 校验注解 | 测试意义 |
|------|-----------|----------|----------|
| 用户名 user_name | varchar(30) NOT NULL | `@NotBlank` + `@Size(max=30)` + `@Xss` | 空值必拦；**注意：实体用 30，但 UserConstants 写的登录长度是 2~20，两处不一致** |
| 昵称 nick_name | varchar(30) NOT NULL | `@Xss` + `@Size(max=30)`，**无 @NotBlank** | 空昵称能过注解校验，但 DB 是 NOT NULL → 可能报 500 |
| 邮箱 email | varchar(50) | `@Email` + `@Size(max=50)`，空串放行 | 空邮箱合法；非法格式才拦 |
| 手机号 phonenumber | varchar(11) | `@Size(max=11)`，**无正则** | 字母/符号能通过（真实 Bug） |
| 密码 password | varchar(100) | 实体类**无校验**（`@JsonProperty` 只读/只写控制） | 密码长度靠前端+登录侧，新增时服务端不二次校验长度 |
| 备注 remark | varchar(500) | 无校验 | 超 500 会 DB 报错 |

### 0.2 唯一性校验（服务层，非数据库约束）

`checkUserNameUnique` / `checkPhoneUnique` / `checkEmailUnique` 三个方法，都是"查库→比对 userId"：

| 规则 | 源码事实 | 测试意义 |
|------|----------|----------|
| 用户名唯一 | 新增/修改都查重，重复返回"登录账号已存在" | 同名必拦 |
| 手机号唯一 | **仅当手机号非空时才校验** | 空手机号可重复 |
| 邮箱唯一 | **仅当邮箱非空时才校验** | 空邮箱可重复 |

### 0.3 删除是「逻辑删除」，不是物理删除

`sys_user` 有 `del_flag` 字段：`0=存在`，`2=删除`。删除用户时执行的是 `UPDATE ... SET del_flag='2'`，**数据还在库里**。

> 这是很多初级测试不知道的点：你删除用户后 `SELECT * FROM sys_user` 查不到，是因为查询自动过滤了 `del_flag='2'` 的记录，不是数据真没了。验证要写 `WHERE del_flag='2'` 才能看到"被删掉"的用户。

### 0.4 特殊保护规则

| 规则 | 源码事实 | 测试意义 |
|------|----------|----------|
| 超级管理员保护 | `checkUserAllowed`：userId=1 抛"不允许操作超级管理员用户" | admin 不能删/改/停用/重置密码 |
| 当前用户保护 | 删除接口：`ArrayUtils.contains(userIds, getUserId())` 返回"当前用户不能删除" | 不能自己删自己 |
| 数据权限 | `checkUserDataScope`：非 admin 只能操作本部门数据 | 越权测试点 |

### 0.5 权限注解（越权测试的基础）

每个接口都挂了 `@PreAuthorize("@ss.hasPermi('system:user:xxx')")`：

| 权限标识 | 对应操作 |
|----------|----------|
| `system:user:list` | 查询列表 |
| `system:user:query` | 查看详情/授权角色 |
| `system:user:add` | 新增 |
| `system:user:edit` | 修改/状态切换/授权角色 |
| `system:user:remove` | 删除 |
| `system:user:resetPwd` | 重置密码 |
| `system:user:export` | 导出 |
| `system:user:import` | 导入 |

> 用普通角色登录（无这些权限）再直接调接口，应返回 403 或"权限不足"——这就是越权/权限测试。

### 0.6 13 个接口一览

```
GET    /system/user/list            列表（分页）
POST   /system/user/export          导出 Excel
POST   /system/user/importData      导入 Excel
POST   /system/user/importTemplate  下载导入模板
GET    /system/user/ 或 /{userId}    获取详情
POST   /system/user                 新增
PUT    /system/user                 修改
DELETE /system/user/{userIds}       删除（支持批量）
PUT    /system/user/resetPwd        重置密码
PUT    /system/user/changeStatus    状态切换
GET    /system/user/authRole/{userId} 查授权角色
PUT    /system/user/authRole        授权角色
GET    /system/user/deptTree        部门树
```

**新增类的三个"杀手级"测试点**（面试必讲）：

1. **手机号能输字母**（USER_023）—— 因为源码 `phonenumber` 只有 `@Size(max=11)` 没有 `@Pattern` 正则，这是真 Bug。
2. **昵称为空**（USER_021）—— 注解没加 `@NotBlank`，但数据库 `NOT NULL`，能测出"前后端校验不一致"。
3. **密码长度**（USER_019）—— 新增接口的实体类对 password 无校验，密码长度可能只在登录/修改密码侧拦截。

| 编号 | 用例标题 | 优先级 | 步骤 | 预期结果 |
|------|----------|--------|------|----------|
| USER_080 | 无权限调用新增接口 | 高 | 用无 `system:user:add` 权限的账号直接 POST | 返回 403 或"权限不足" |
| USER_081 | 无权限调用删除接口 | 高 | 无 remove 权限直接 DELETE | 返回 403 |
| USER_082 | 普通用户查全部用户 | 高 | 普通角色调 list 接口 | **只返回本部门数据（数据权限），非全部** |
| USER_083 | 普通用户改其他部门用户 | 高 | 越权调用 edit | 返回无权限，数据不变 |
| USER_084 | 未登录调用接口 | 高 | 不带 token 调 /system/user/list | 返回 401 |
| USER_085 | 伪造 token 调用 | 高 | 篡改 token 内容后调用 | 返回 401 |

**权限测试要点**：RuoYi 用 Spring Security + 自定义 `@PreAuthorize` 注解控制按钮级权限，用**数据权限（部门维度）**控制数据范围。测试要区分两种失败：**无按钮权限**（403）和**无数据权限**（返回空/越权被拦）。

## 十、数据库验证 SQL（核心，务必做）

用户管理每个操作都要用 SQL 核对，尤其是**逻辑删除**和**关联表**。

```sql
-- 1. 新增后验证（密码必须是 BCrypt 密文，不是明文）
SELECT user_id, user_name, nick_name, phonenumber, email, status, del_flag,
       LEFT(password, 7) AS pwd_prefix, create_time
FROM sys_user WHERE user_name = 'test001';
-- 预期：pwd_prefix = '$2a$10$'，status=0，del_flag=0

-- 2. 修改后验证（update_time 变化）
SELECT nick_name, phonenumber, update_time FROM sys_user WHERE user_name='test001';

-- 3. 删除后验证【关键】—— 逻辑删除，数据还在
SELECT user_id, user_name, del_flag FROM sys_user WHERE user_name='test001';
-- 普通查询查不到（被过滤）
-- 但这样查能看到：
SELECT user_id, user_name, del_flag FROM sys_user WHERE user_name='test001' AND del_flag='2';
-- 预期：del_flag 从 0 变 2，记录物理上仍存在

-- 4. 用户-角色关联表验证
SELECT u.user_name, r.role_name, r.role_key
FROM sys_user u
JOIN sys_user_role ur ON u.user_id = ur.user_id
JOIN sys_role r ON ur.role_id = r.role_id
WHERE u.user_name = 'test001';

-- 5. 删除用户后，验证关联表已被清理【进阶加分项】
SELECT * FROM sys_user_role WHERE user_id = (SELECT user_id FROM sys_user WHERE user_name='test001' AND del_flag='2');
-- 预期：返回空，说明 sys_user_role 已同步物理清理，无脏数据残留

-- 6. 验证默认密码配置
SELECT config_value FROM sys_config WHERE config_key='sys.user.initPassword';

-- 7. 验证手机号字段实际能存字母（Bug 复现证据）
SELECT user_name, phonenumber FROM sys_user WHERE phonenumber REGEXP '[a-zA-Z]';
```

**为什么要做 SQL 验证**：前端"看起来成功了"不等于"数据真的对了"。测试工程师的价值就在于——你操作完点一下，能拿出数据库证据说"这条记录的 del_flag 变成了 2，password 是 BCrypt 密文，关联表已正确清理"。

## 十一、Bug 报告示例（真实 Bug）

### Bug 1：手机号能输字母（最高价值，真实存在）

```markdown
【Bug 编号】BUG_USER_001
【模块】用户管理
【标题】[用户管理] 新增用户时手机号输入 11 位字母仍能保存成功

【严重程度】一般
【优先级】中

【环境】Chrome 120 / Spring Boot 2.5.15 / MySQL 8.0

【前置条件】已用 admin 登录

【复现步骤】
1. 进入 系统管理 → 用户管理 → 新增
2. 手机号输入 "abcdefghijk"（11 位字母）
3. 其余必填项正常填写，点确定

【实际结果】
新增成功，列表显示手机号为 abcdefghijk，数据库 phonenumber 字段也存了字母

【预期结果】
手机号应为 11 位数字，输入字母应提示"手机号格式错误"并阻止保存

【原因分析】（测试可附）
SysUser.java 中 phonenumber 字段仅加了 @Size(max=11) 校验，
没有 @Pattern(regexp="^1[3-9]\\d{9}$") 正则校验

【复现频率】必现

【附件】新增成功截图 + 数据库 phonenumber 查询结果
```

### Bug 2：昵称为空导致 500，并把完整 SQL 报错返回给前端（含信息泄露）

```markdown
【Bug 编号】BUG_USER_002
【模块】用户管理
【标题】[用户管理] 新增用户昵称为空时后端报 500，并把完整 SQL 错误返回给前端

【严重程度】一般（含信息泄露）
【优先级】中

【环境】Spring Boot 2.5.15 / MySQL 8.0

【前置条件】已用 admin 登录

【复现步骤】
1. 进入 系统管理 → 用户管理 → 新增
2. 用户名/部门/密码正常填写，昵称留空（或清空成空串）
3. 点确定

【实际结果】
接口返回 code=500，msg 为完整 SQL 异常：
"Field 'nick_name' doesn't have a default value"，
并附带了 insert into sys_user(...) 的完整 SQL 语句和表结构信息

【预期结果】
1. 昵称为空应有友好提示（如"昵称不能为空"），不应报 500
2. 后端异常不应把 SQL、表名、字段名等内部信息暴露给前端

【原因分析】（测试可附）
SysUser.nickName 字段只有 @Xss + @Size，没有 @NotBlank 校验；
且 SysUserMapper.insertUser 对 nick_name 用 <if test="nickName != null and nickName != ''"> 空值过滤，
导致昵称为空时 SQL 不包含 nick_name 列，而数据库该列 NOT NULL 且无默认值，最终插入失败抛 SQL 异常。

【复现频率】必现

【附件】接口返回的 500 响应体（含 SQL 报错）
```

**你在这套用例里练到的核心能力**：

1. **读源码设计用例** —— 从 `@Size`/`@NotBlank`/`@Email` 注解里挖出校验规则，而不是拍脑袋猜
2. **发现真实 Bug** —— 手机号无正则校验、昵称无 @NotBlank 导致 500 且 SQL 信息泄露
3. **逻辑删除 vs 物理删除** —— 理解了 del_flag 机制，能写出"删除后数据还在"的验证 SQL
4. **关联表清理验证** —— 删除用户后确认关联表被物理清理，无脏数据
5. **权限与越权测试** —— 区分按钮权限（403）和数据权限（部门范围）

面试可以这样讲：

> "我在 RuoYi 上做用户管理模块测试，没有停留在 CRUD 表面。我先读了 SysUser 实体类，发现手机号字段只有 `@Size` 长度校验、没有正则格式校验，于是专门测了'手机号输字母'这个场景，果然能保存成功，提了 Bug；还发现昵称字段没有 `@NotBlank`，昵称留空时后端直接 500 还把 SQL 报错返回给前端，是典型的校验缺失+信息泄露。我还搞清楚了删除是逻辑删除——数据其实还在库里，只是 del_flag 变了，所以我的删除用例都会额外查一次 `WHERE del_flag='2'` 验证数据状态，并确认删除后角色关联表被正确清理。这些都是读源码才能测出来的点。"

## 附：与登录模块的关联

用户管理是"数据侧"，登录模块是"入口侧"，两者通过 `status`、`del_flag`、`password` 字段串起来：

- 用户管理**停用**某用户（status=1）→ 该用户**登录**时提示"用户已封禁，请联系管理员"（登录用例 LOGIN_028）
- 用户管理**重置密码**→ 该用户旧密码**登录失败**（登录用例 LOGIN_017）
- 用户管理**删除**用户（del_flag=2）→ 该用户**登录**时提示"对不起，您的账号已被删除"（message key: user.password.delete）

> 面试时把两个模块串起来讲，能证明你理解的是"系统整体"，而不是孤立的一个个功能点。
