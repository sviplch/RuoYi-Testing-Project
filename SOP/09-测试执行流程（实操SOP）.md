## 三、执行顺序：5 天实操安排

按「从简单到复杂、从单模块到端到端」的顺序跑。每天结束前把当天的结果记下来。

## 四、单条用例的标准执行动作（核心心法）

拿到一条用例，不要乱点，固定走这 6 步：

```
1. 读前置条件 → 确认满足（不满足先造数据）
2. 按步骤操作 → 只做用例里写的那几步，别多加戏
3. 观察实际结果 → 和预期逐字对比，不是"大概对了"
4. 记录 → 通过 / 失败（写到用例表后面的"实际结果"栏）
5. 失败就留证 → 截图 + 接口返回 + 复现 3 次确认是必现
6. 涉及数据 → SQL 核对（写操作必查，读操作抽查）
```

**关键原则**：
- 「预期结果要具体」：不是"显示正确"，是"返回 code=200，页面提示『修改成功』，sys_user 表该行 phonenumber 已更新"
- 「通过/失败如实记」：**不要为了报告好看把失败改成通过**。一个真实记录的失败用例，比十个人为修饰的通过更有价值——面试官会追问你的失败用例。
- 「留证据」：截图、接口响应体、SQL 结果，三者至少留一个，方便回溯。

## 五、三种测试手段怎么配合

一次测试 = 界面 + 接口 + 数据库，三个视角交叉验证：

| 手段 | 工具 | 测什么 | 什么时候用 |
|------|------|--------|-----------|
| 界面测试 | 浏览器 + F12 | 主流程、提示语、页面展示、前端校验 | 所有用例的第一遍 |
| 接口测试 | Postman | 绕过前端、直连后端、越权、异常参数 | 前端校验会被绕过时；越权测试 |
| 数据库验证 | SQL | 数据是否真的落库、关联表、脏数据 | 所有写操作之后 |

**举个具体例子（新增用户）**：
1. 界面：填表单点保存，看到「新增成功」提示
2. 接口：Postman 直接 POST /system/user，确认后端 code=200
3. 数据库：`SELECT user_name, phonenumber FROM sys_user WHERE user_name='test01'`，确认这条真的进了表、字段值对

**三者结论一致，这条用例才算真通过**。任何一个对不上，就是 Bug。

## 六、Postman 接口测试流程（完整版）

### 6.1 准备：建环境变量

在 Postman 里建一个 Environment「RuoYi」，加这几个变量：

| 变量名 | 初始值 | 说明 |
|--------|--------|------|
| baseUrl | http://localhost:8080 | 后端地址 |
| token | （空） | 登录后自动填 |
| uuid | （空） | 验证码 uuid，captchaImage 返回 |
| code | （空） | 验证码明文，从 Redis 读 |

### 6.2 登录链路（三步）

**第一步：拿验证码**

```
GET {{baseUrl}}/captchaImage
```
返回：`{ "code":200, "img":"...base64...", "uuid":"xxxx", "captchaEnabled":true }`。把 uuid 存进环境变量。

**第二步：从 Redis 读验证码明文**

RuoYi 的验证码明文存在 Redis 里，key 是 `captcha_codes:{uuid}`。在终端执行：

```bash
"C:/Program Files/Redis/redis-cli.exe" get "captcha_codes:把uuid贴进来"
```
拿到 4 位验证码（如 `3ab5`），存进 `code` 变量。

**第三步：登录拿 token**

```
POST {{baseUrl}}/login
Body（JSON）：
{
  "username": "admin",
  "password": "admin123",
  "code": "{{code}}",
  "uuid": "{{uuid}}"
}
```
返回 `{ "code":200, "msg":"操作成功", "token":"eyJhbGci..." }`。

**自动存 token**：在登录请求的 Tests 里写：

```javascript
const json = pm.response.json();
if (json.code === 200) {
    pm.environment.set("token", json.token);
    pm.test("登录成功", () => pm.expect(json.code).to.eql(200));
}
```

### 6.3 带 token 调受保护接口

所有业务接口都要加请求头：

```
Authorization: Bearer {{token}}
```

| 接口 | 用途 |
|------|------|
| GET /getInfo | 当前用户信息 |
| GET /getRouters | 当前用户菜单 |
| GET /system/user/list?pageNum=1&pageSize=10 | 用户列表 |
| POST /system/user | 新增用户 |
| PUT /system/user | 修改用户 |
| DELETE /system/user/{userIds} | 删除用户 |
| PUT /system/user/resetPwd | 重置密码 |
| PUT /system/user/changeStatus | 状态切换 |
| GET /system/role/list | 角色列表 |

### 6.4 断言模板

每个请求的 Tests 里都写三句：

```javascript
const json = pm.response.json();
pm.test("HTTP 状态码 200", () => pm.response.to.have.status(200));
pm.test("业务 code=200", () => pm.expect(json.code).to.eql(200));
pm.test("msg=操作成功", () => pm.expect(json.msg).to.eql("操作成功"));
```

### 6.5 复现手机号 Bug（接口版）

直接 POST /system/user，`phonenumber` 填 `abcdefghijk`（11 位字母），观察是否保存成功——这就是 BUG_USER_001 的接口复现，比界面更有说服力。

### 6.6 批量回归（Collection Runner）

把登录 + 主要接口存成一个 Collection，用 Runner 一键跑，几秒出全部结果，作为「回归测试」的证据。

## 七、执行结果怎么记录

建议在每条用例表后面补两列，执行时直接填：

```
用例编号 | ... | 预期结果 | 实际结果 | 是否通过
LOGIN_001 | ... | 登录成功跳转首页 | 登录成功，跳转首页，返回 token | 通过
LOGIN_005 | ... | 提示密码不能为空 | 提示"密码不能为空" | 通过
USER_012 | ... | 提示手机号格式错误 | 11 位字母仍保存成功 | 失败（BUG_USER_001）
```

**不用每条都写得花哨**，失败用例写清楚现象，通过用例写「通过」+ 关键提示即可。
