# 05 — 企业测试全流程文档体系

> 真实公司里，测试工程师的价值有一半体现在"文档"上——你测得再好，如果文档写不清，等于白测。本文件讲清楚：测试前、中、后分别要产出哪些文档，每个文档给谁看、怎么写、长什么样。

---

## 一、测试为什么要写文档

1. **可追溯**：出了问题能查回"当初是谁测的、测了哪些、结论是什么"
2. **可复用**：回归测试时直接拿上次的用例跑，不用重新想
3. **可交付**：测试报告是发布决策的依据，不是口头说"测完了"
4. **合规要求**：金融、政企、医疗等项目，文档是强制审计项

一句话：**文档是你测试工作的"证据"，没有文档的测试等于没测。**

---

## 二、测试全流程文档总览

```
┌─────────────────────────────────────────────────────────┐
│                    测试前（准备阶段）                        │
│                                                          │
│  1. 需求分析记录（测试对需求的理解和疑问）                      │
│  2. 测试计划（测什么、怎么测、测多久）                        │
│  3. 测试用例（具体怎么测，一条条写清楚）                       │
│  4. 测试用例评审记录（大家看过用例，确认没漏）                  │
│  5. 测试环境/数据准备清单（用什么环境、造什么数据）              │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    测试中（执行阶段）                        │
│                                                          │
│  6. 测试用例执行记录（每条用例跑的结果，通过/失败）             │
│  7. 缺陷报告 / Bug单（发现问题，一条条写清楚）                 │
│  8. 测试日报（每天向团队汇报进度）                            │
│  9. 缺陷跟踪表（所有Bug的状态汇总）                           │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    测试后（收尾阶段）                        │
│                                                          │
│ 10. 测试报告（总结测试结果，给质量结论）                       │
│ 11. 遗留问题清单（没修完的问题，明确告知）                     │
│ 12. 发布/上线检查清单（能不能上线的最后确认）                   │
│ 13. 测试资产归档（用例、脚本、数据沉淀下来）                    │
└─────────────────────────────────────────────────────────┘
```

**应届生/初级测试要会写的**（重点）：测试用例、缺陷报告、测试日报、测试报告、用例执行记录。

**资深/负责人主导的**：测试计划、测试方案、需求分析、发布决策。

## 三、测试前文档（5个）

### 文档1：需求分析记录

**什么时候写**：拿到需求文档后，动手写用例之前。

**给谁看**：产品经理、开发、测试负责人。

**核心作用**：把你对需求的理解写下来，把看不懂的地方列出来，防止后面测错了方向。

**模板**：

```markdown
# 需求分析记录

## 一、需求概述
【XXX模块】本次要实现【XXX功能】，服务对象是【XXX】。

## 二、功能点拆解
| 功能点 | 说明 | 涉及页面/接口 |
|--------|------|--------------|
| 用户新增 | 管理员录入新用户 | 用户管理页 + /system/user 接口 |

## 三、需求疑问（测试向产品/开发确认）
| 序号 | 疑问 | 我的理解 | 结论 |
|------|------|----------|------|
| 1 | 密码最少几位？ | 需求没写，我理解是5位 | 待产品确认 |
| 2 | 用户名能否重复？ | 应该唯一 | 待确认 |

## 四、测试范围初步判断
- 重点测：新增、查询、权限
- 次要测：界面样式
```

---

### 文档2：测试计划

**什么时候写**：需求评审通过后，正式开始测之前。

**谁主导**：测试负责人写，初级测试参与讨论。

**给谁看**：项目经理、开发、产品、测试团队。

**核心作用**：定方向——测什么、不测什么、怎么测、花多久、有什么风险。

**模板**：

```markdown
# 测试计划

## 一、测试目标
验证【XXX系统】的【XXX模块】功能正确、数据准确、异常可容错，
达到可发布的质量标准。

## 二、测试范围
- 包含：登录模块、用户管理模块、角色管理模块
- 不包含：性能压测（本轮不做）、安全渗透测试（第三方做）

## 三、测试类型与策略
| 测试类型 | 策略 | 工具 |
|----------|------|------|
| 功能测试 | 黑盒，等价类+边界值+场景法 | 手工 |
| 接口测试 | 正常+异常参数覆盖 | Postman |
| 数据库验证 | 操作后SQL核对 | Navicat |
| 回归测试 | 修复后重跑核心用例 | 手工 |

## 四、测试环境
| 环境项 | 配置 |
|--------|------|
| 操作系统 | Windows 11 |
| 后端 | Spring Boot 2.5.15 (8080) |
| 前端 | Vue2 (80) |
| 数据库 | MySQL 8.0 (ry_vue) |

## 五、测试排期
| 阶段 | 时间 | 产出 |
|------|------|------|
| 需求分析 | X月X日 | 需求分析记录 |
| 用例设计 | X月X日-X日 | 测试用例 |
| 用例评审 | X月X日 | 评审记录 |
| 测试执行 | X月X日-X日 | 用例执行记录、Bug单 |
| 回归测试 | X月X日 | 回归结果 |
| 测试报告 | X月X日 | 测试报告 |

## 六、人员分工
| 人员 | 职责 |
|------|------|
| 测试负责人 | 计划、报告、决策 |
| 测试工程师（我） | 用例设计、执行、Bug跟踪 |

## 七、风险与应对
| 风险 | 应对 |
|------|------|
| 环境不稳定 | 提前搭好备用环境 |
| 需求变更频繁 | 及时同步，变更后重评审 |
```

### 文档3：测试用例（核心中的核心）

**什么时候写**：测试计划之后，执行之前。

**谁写**：测试工程师（你）。

**给谁看**：开发、产品、测试同事（评审时）。

**核心作用**：把"怎么测"落到一条条可执行的步骤，是测试执行和回归的蓝本。

**完整用例字段**（我之前的实战文档里有，这里强调规范）：

| 字段 | 说明 | 示例 |
|------|------|------|
| 用例编号 | 唯一，可追溯 | USER_001 |
| 模块 | 所属功能 | 用户管理 |
| 用例标题 | 一句话说清 | 新增用户-用户名重复时提示错误 |
| 优先级 | 高/中/低 | 高 |
| 前置条件 | 执行前状态 | 已用admin登录 |
| 测试步骤 | 编号+动宾 | 1.进入用户管理 2.点新增... |
| 输入数据 | 具体填什么 | 用户名=admin |
| 预期结果 | 明确可验证 | 提示"用户名已存在" |
| 实际结果 | 执行后填 | - |
| 是否通过 | 通过/失败/阻塞 | - |

**一个好用例的标准**：别人拿你的用例，不看你人，也能测出一样的结果。

### 文档4：测试用例评审记录

**什么时候写**：用例写完、执行之前。

**谁参与**：测试（我）、开发、产品。

**核心作用**：让大家确认"用例没漏测、没误解需求"，也是需求的二次确认。

**模板**：

```markdown
# 测试用例评审记录

## 评审信息
- 评审时间：X月X日
- 评审对象：登录模块、用户管理模块用例（共XX条）
- 参与人：测试XX、开发XX、产品XX

## 评审结论
☑ 通过（可执行）
☐ 修改后通过
☐ 不通过

## 评审问题与修改
| 序号 | 问题 | 提出人 | 处理结果 |
|------|------|--------|----------|
| 1 | 密码长度需求没写，用例按5位设计是否合理 | 开发 | 产品确认为5位，用例OK |
| 2 | 缺"批量删除"用例 | 产品 | 补充 USER_024 |

## 遗留事项
无
```

### 文档5：测试环境/数据准备清单

**什么时候写**：执行前。

**核心作用**：保证环境可用、数据够用，避免执行时才发现缺数据。

**模板**：

```markdown
# 测试环境与数据准备清单

## 环境准备
| 项目 | 状态 |
|------|------|
| 后端服务启动 | ✅ |
| 前端可访问 | ✅ |
| 数据库连接正常 | ✅ |
| Redis运行 | ✅ |

## 测试数据准备
| 数据 | 用途 | 数量 | 状态 |
|------|------|------|------|
| 普通用户账号 | 测查询/修改/删除 | 5个 | ✅ |
| 停用状态账号 | 测状态切换 | 2个 | ✅ |
| 超长用户名 | 测边界 | 1个 | ✅ |

## 测试账号
| 账号 | 密码 | 角色 |
|------|------|------|
| admin | admin123 | 超级管理员 |
| test001 | 12345 | 普通角色 |
```

## 四、测试中文档（4个）

### 文档6：测试用例执行记录

**本质**：就是在用例表上补两列——"实际结果"和"是否通过"。不需要单独一个文件，直接往用例表里填。

**关键规范**：
- 通过的用例：`实际结果` 写"与预期一致"或具体结果
- 失败的用例：`实际结果` 写清楚哪里和预期不符，并关联 Bug 编号

| 用例编号 | ... | 实际结果 | 是否通过 |
|----------|-----|----------|----------|
| USER_008 | ... | 新增成功，列表显示test001 | 通过 |
| USER_010 | ... | 提示"用户名已存在" | 通过 |
| USER_013 | ... | 密码5位新增失败，提示长度不足 | 失败(BUG_001) |

### 文档7：缺陷报告（Bug 单）

**什么时候写**：发现 Bug 时，立刻写。

**给谁看**：开发（要修复）、测试负责人（要统计）。

**核心作用**：让开发能复现并定位问题。**写不好 Bug 单的测试，会被开发嫌弃。**

**Bug 单完整字段**（之前实战文档有，这里给最规范的版本）：

```markdown
【Bug标题】[模块] 在[条件]下出现[现象]

【严重程度】致命 / 严重 / 一般 / 轻微 / 建议
【优先级】高 / 中 / 低

【测试环境】
- 版本：V1.0
- 浏览器：Chrome 120
- 后端/数据库：...

【前置条件】
已用 admin 登录

【复现步骤】
1. ...
2. ...
3. ...

【实际结果】
（截图 + 文字）

【预期结果】
（需求文档原文）

【复现频率】必现 / 偶现（10次中3次）

【附件】
截图、日志、抓包文件
```

**严重程度分级标准**（企业通用）：

| 级别 | 定义 | 举例 |
|------|------|------|
| 致命 | 系统崩溃、数据丢失、核心流程完全不可用 | 登录接口500，所有人进不去 |
| 严重 | 核心功能部分不可用，无规避方法 | 新增用户后无法保存 |
| 一般 | 功能异常但有规避方法 | 手机号校验不严，可手动纠正 |
| 轻微 | 不影响使用，体验/UI问题 | 按钮文字错位 |
| 建议 | 改进建议，不算Bug | 提示语可以更友好 |

---

### 文档8：测试日报

**什么时候写**：每天下班前。

**给谁看**：测试负责人、项目经理。

**核心作用**：让团队知道测试进度、卡在哪、风险是什么。**应届生必会，且最能体现你靠不靠谱。**

**模板**：

```markdown
# 测试日报（X月X日）

## 今日完成
- 执行登录模块用例 10 条，通过 8 条，失败 2 条
- 提交 Bug 3 个（BUG_001~003）
- 完成用户管理模块用例设计 20 条

## 明日计划
- 执行用户管理模块用例
- 跟进 BUG_001 修复情况

## 风险与问题
- BUG_002 是致命问题，开发说涉及底层改动，可能影响上线时间，已上报负责人
```

**日报三要素：做了什么 + 明天做什么 + 有什么风险。**

---

### 文档9：缺陷跟踪表

**什么时候维护**：整个测试执行期间持续更新。

**核心作用**：一眼看清所有 Bug 的状态、谁在负责、还剩多少没解决。

**模板**（Excel 表格）：

| Bug编号 | 标题 | 严重程度 | 状态 | 提交人 | 处理人 | 提交时间 | 修复时间 | 验证结果 |
|---------|------|----------|------|--------|--------|----------|----------|----------|
| BUG_001 | 密码5位校验失败 | 严重 | 已修复 | 我 | 张三 | X月X日 | X月X日 | 已验证通过 |
| BUG_002 | 登录接口缺 code 字段空指针 | 一般 | 处理中 | 我 | 李四 | X月X日 | - | - |
| BUG_003 | 手机号校验不严 | 一般 | 暂缓 | 我 | 张三 | X月X日 | - | - |

**Bug 状态流转**：新建 → 已确认 → 处理中 → 已修复 → 已验证 → 关闭（或 重新打开/拒绝/暂缓）

## 五、测试后文档（4个）

### 文档10：测试报告（核心交付物）

**什么时候写**：所有测试执行完、回归完成后。

**谁主导**：测试负责人写，初级测试提供数据。

**给谁看**：项目经理、产品、开发、甚至客户。

**核心作用**：给质量下一个结论——能不能发布，还有哪些风险。

**完整模板**：

```markdown
# 测试报告

## 一、测试概述
- 项目/系统：若依后台管理系统
- 测试模块：登录、用户管理
- 测试周期：X月X日 - X月X日
- 测试类型：功能测试、接口测试
- 测试人员：XX

## 二、测试范围
（引用测试计划里的范围，说明实际测了哪些）

## 三、测试结果统计
| 指标 | 数据 |
|------|------|
| 用例总数 | 40 |
| 已执行 | 40 |
| 通过 | 36 |
| 失败 | 3 |
| 阻塞 | 1 |
| 通过率 | 90% |

## 四、缺陷统计
| 指标 | 数据 |
|------|------|
| Bug总数 | 5 |
| 致命/严重 | 1 |
| 一般 | 3 |
| 轻微/建议 | 1 |
| 已修复并验证 | 4 |
| 遗留未解决 | 1 |

## 五、主要问题及影响分析
1. BUG_002（登录接口缺 code 字段空指针）：缺参未做空值判断导致空指针，属接口健壮性问题，建议下版本修复。
2. BUG_001（密码5位校验失败）：已修复并回归通过。

## 六、质量结论
【☑ 通过，可发布】/【☐ 有条件通过】/【☐ 不通过】
本模块核心功能正常，关键异常已处理，遗留1个一般级问题不影响主流程，建议发布。

## 七、遗留问题
（引用遗留问题清单）

## 八、经验总结
- 本次发现需求文档对密码长度描述不清，已反馈产品补充
- 边界值用例发现的Bug最多，后续用例设计继续加强边界覆盖
```

### 文档11：遗留问题清单（Known Issues）

**核心作用**：诚实告诉团队"还有这些问题没解决"，防止上线后措手不及。

**模板**：

```markdown
# 遗留问题清单

| 编号 | 问题描述 | 严重程度 | 影响范围 | 暂缓原因 | 计划解决版本 |
|------|----------|----------|----------|----------|-------------|
| 1 | 登录接口缺 code 字段空指针 | 一般 | 接口健壮性 | 补空值判断 | V1.1 |
| 2 | 手机号校验不严格 | 轻微 | 数据质量 | 优先级低 | 待定 |
```

---

### 文档12：发布/上线检查清单

**核心作用**：上线前最后一道关，逐项确认，避免遗漏。

**模板**：

```markdown
# 发布检查清单

## 测试侧
- [ ] 所有致命/严重 Bug 已修复并验证通过
- [ ] 回归测试通过率 ≥ 95%
- [ ] 测试报告已发出
- [ ] 遗留问题已同步产品/客户

## 环境侧
- [ ] 生产环境数据库脚本已执行
- [ ] 生产环境配置已核对
- [ ] 版本号一致

## 数据侧
- [ ] 生产数据备份已完成
- [ ] 测试数据未混入生产库

## 结论
☑ 可发布  ☐ 不可发布
```

---

### 文档13：测试资产归档

**核心作用**：把这次测试的产出沉淀下来，下次回归、下个项目复用。

**归档清单**：
- 测试用例（放进用例库，形成资产）
- Bug 单（形成缺陷库，统计历史Bug类型）
- 测试报告
- 自动化脚本（如果有）
- 测试数据脚本（造数据的SQL）

---

## 六、文档之间的流转关系

```
需求文档 → 需求分析记录 → 测试计划 → 测试用例 → 用例评审记录
                                              ↓
                                    测试环境/数据清单
                                              ↓
                                    用例执行记录（每天更新）
                                              ↓
                             缺陷报告 ←→ 缺陷跟踪表 ←→ 测试日报
                                              ↓
                                    回归测试（复用用例）
                                              ↓
                                    测试报告 → 遗留问题清单 → 发布检查清单
                                              ↓
                                    测试资产归档
```

## 七、给应届生的实操建议

1. **重点先掌握 4 个文档**：测试用例、缺陷报告、测试日报、测试报告。这 4 个是你一入职就会被要求写的东西。

2. **测试日报最能体现职业度**：很多应届生不写日报或写得很水。你如果能每天清晰汇报"做了什么、卡在哪、有什么风险"，主管对你的印象会非常好。

3. **Bug 单要写到开发挑不出毛病**：环境清楚、步骤可复现、有截图、有日志。这是测试工程师的基本功。

4. **测试计划、需求分析**这类文档，你初期是"参与"不是"主导"，但你要看得懂、能在评审会上提出自己的意见。

5. **把你在 RuoYi 上练的成果，按这套文档体系整理出来**——一份测试计划 + 一份用例 + 几个Bug单 + 一份测试报告，这就是你面试时能拿出来的"项目经历"。
